# 迁移、备用启用与恢复

用户选择的策略是：**迁移所选主 Web 的数据库和题库，再切换关联评测机**。

## 正常切换

1. 先添加另一台机器作为备用 Web，用同一镜像标签执行资源准备。
2. 安排维护时间，停止选手继续提交，等待待评测队列清空。
3. 在“状态与主备切换”选择备用 Web 与来源主 Web，勾选维护操作确认。
4. 程序检查源站可登录、目标为空、空间足够，以及目标缓存镜像 ID 与源站正在运行的镜像一致。
5. 停止源站和关联评测容器，检查 MySQL 容器为正常退出，归档完整 `data` 目录。
6. 快照经 SSH 下载到 Windows，校验 SHA256，再上传目标机并恢复。
7. 目标使用来源站点标识、数据库和管理员口令启动，保留来源数据库名。目标 IP 和 SSH 配置仍使用备用机的配置。
8. 检查登录、CSS，以及 users / problem / contest / solution 的数量；对停止瞬间处于编译或运行状态的提交重新排队。
9. 重建关联评测机的连接，逐台确认新的 OJ 心跳。
10. 成功后源站角色变为备用且容器保持停止；目标变为启用。原数据和快照不删除。

这会中断比赛访问，宜在赛前演练或维护窗口使用。工具不设置虚拟 IP、不修改路由或 DNS，选手需要使用新 Web 地址，或由部署人员在验证后修改入口 DNS/反向代理。

冷迁移复制整个数据目录，包括 MySQL 数据文件、题库、站点文件和配置。**源/目标镜像必须完全一致**，不在迁移时升级 MySQL 或 OJ。同一个 exp 标签被重新推送也可能对应不同镜像，必须比较实际 ID。

## 失败后

程序尝试停止目标，重新启动源站，再将评测机绑定回源站。如果任何恢复动作失败，日志会标明“恢复未完成”，不能仅凭配置里的角色认为恢复成功；需要检查两台 Web 的容器与各评测心跳。

目标已经解压的数据保留，重试应新增节点并使用新的空目录。不要直接清空旧数据，也不要手工把已有数据库目录混在一起。

旧源站带有保留数据，不能作为空白备用直接反向迁移。完成备份并确认保留策略后，由部署人员准备另一处空目录。

## 只做备份

选择启用 Web，点击“备份 Web 到本机”。程序短暂停机，下载归档并校验，然后恢复原 Web 和评测机。

本机文件：

```text
%LOCALAPPDATA%\CSGOJDeploy\backups\<节点>-<时间>\data.tar.gz
%LOCALAPPDATA%\CSGOJDeploy\backups\<节点>-<时间>\manifest.json
```

另行下载“部署信息与口令”。归档和私钥应按敏感资料保管。DPAPI 配置绑定当前 Windows 用户，搬到另一台电脑不保证能解密；业务口令导出和私钥备份应单独保存。

## 源站已经失联

自动迁移要求源站在线，无法从失联机器读取最新数据。使用最近备份人工恢复时：

1. 确认旧站已停止或与比赛网络隔离，防止两台站点同时接受提交。
2. 核对 `manifest.json` 的版本与 SHA256，明确快照时间，接受快照之后数据可能缺失。
3. 在备用机准备完全一致的镜像，上传归档到空的专用项目目录。
4. 检查归档内容只在 `data/` 内，没有指向目录外的路径或链接，再恢复。保留数字 UID/GID。

```bash
cd <新的空项目目录>
sha256sum data.tar.gz
tar -tzf data.tar.gz | head
sudo tar --numeric-owner -xzpf data.tar.gz -C <新的空项目目录>
```

5. 使用来源站点标识、原 SQL 和 phpMyAdmin 口令，以及原镜像标签调用官方 `up`。不要重新初始化管理员。
6. 登录验证数据后，按原评测账号口令重建评测机，修改 `--server-url` 为新地址。
7. 做一次真实提交确认评测结果，再开放给选手。

本工具不会自动接管这份人工恢复的目录，避免把来源不明的数据当作空白部署。人工恢复和自动托管是两种明确的恢复路径。
